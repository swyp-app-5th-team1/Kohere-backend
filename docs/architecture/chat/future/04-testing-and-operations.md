# 후속 고도화 테스트와 운영

## 1. 필수 테스트

### 관리자 신고 처리

- `ADMIN`만 목록·상세·상태 변경 가능
- 사용자용 API가 증거·관리자 메모·신고 대상 ID를 노출하지 않음
- 동일 신고를 두 운영자가 처리할 때 optimistic lock 충돌
- 상태 변경과 `report_status_history`가 한 트랜잭션으로 저장
- 최종 증거 append와 완료 시각·보관 만료일 저장의 원자성
- 종결 후 새 대화가 있을 때만 재신고 허용
- active hold가 있으면 신고 자료 정리 보류

### 3개월 만료와 물리 삭제

- 3 calendar months 계산 경계
- 직접 재진입이나 실제 새 메시지가 기존 삭제 주기를 취소하지 않음
- 사용자 삭제 시각부터 3 calendar months를 계산
- 한쪽만 만료되면 TEXT 원문·번역본·BOOKING_CARD 물리 삭제 0건
- 양쪽 공통 경계까지만 삭제
- 번역본을 먼저 삭제한 뒤 TEXT·BOOKING_CARD 메시지를 삭제해 고아 데이터가 남지 않음
- prefix 삭제 후 방의 마지막 메시지 포인터 정합성
- room hold가 있으면 삭제 보류
- 만료 작업 재실행의 멱등성
- SEND·신고 snapshot과 정리 job의 lock 순서·동시성

### 관리자 채팅방 복구

- 일반 사용자용 복구 route가 없고 `ADMIN`만 실행 가능
- 해당 사용자의 가장 최근 `WAITING` 삭제만 복구
- 삭제 직전 메시지 숨김 경계와 방 표시 상태를 정확히 복원
- 상대방 화면·차단·신고 상태는 변경하지 않음
- 반복 복구는 감사 기록을 중복 생성하지 않음
- 더 최근 삭제, `FINALIZED`, 물리 삭제 상태는 `409`
- 관리자 복구와 3개월 만료 작업이 동시에 실행돼도 둘 중 하나만 성공
- snapshot schema 도입 전 삭제는 추측해서 복구하지 않음

## 2. 구현 순서

1. 관리자 계정과 `ADMIN` 인증·인가
2. 신고 상태·처리 결과 code와 운영 절차 확정
3. report 상태 이력·증거 version·hold migration
4. 관리자 목록·상세·상태 변경 API
5. 사용자별 삭제 snapshot과 3개월 만료 경계 migration
6. 관리자 최근 삭제 조회·복구 API와 감사 기록
7. 사용자별 만료 확정 job
8. 양쪽 공통 메시지·번역본 물리 삭제 job
9. 신고 자료 보관 만료 job
10. 통합 테스트·지표·경보·실패 재처리 운영

## 3. 운영 지표

- 관리자 신고 처리 목표일 초과 건수
- 상태 변경 충돌·실패 건수
- 3개월 만료 후보·처리 완료·실패 수
- 물리 삭제 대상 message·translation 수
- hold로 보류된 방·신고 수
- 가장 오래 지연된 정리 작업 시간
- batch 실행 시간과 재시도 수

정기 작업은 작은 batch와 방 단위 트랜잭션으로 실행하며, 일부 실패가 전체 정리를 막지 않게 한다.

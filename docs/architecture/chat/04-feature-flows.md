# 기능별 흐름

이 문서는 여러 API와 내부 기능이 사용자 행동 하나를 어떻게 완성하는지 설명한다. 요청·응답 필드는 [02-api-contracts.md](02-api-contracts.md), 실시간 통신은 [03-websocket-stomp.md](03-websocket-stomp.md), 내부 상태는 [06-data-model-and-retention.md](06-data-model-and-retention.md)가 정본이다.

## 1. 문의하기

1. 세입자가 매물 상세에서 문의하기를 누른다.
2. 앱이 `POST /api/v1/listings/{listingId}/inquiries`를 호출한다.
3. 서버가 로그인 완료 사용자, 세입자 여부, 매물 공개 상태를 확인한다.
4. listing 공개 API에서 `landlordId`와 매물 표시 정보를 얻는다.
5. 본인 매물과 양방향 차단 관계를 검사한다.
6. `(listingId, tenantId, landlordId)` 방을 원자적으로 조회 또는 생성한다.
7. 신규이면 방과 정확히 두 member를 한 트랜잭션으로 저장한다.
8. 사용자 직접 진입이므로 요청자에게 숨겨진 기존 방이면 다시 목록에 표시한다. 이전 메시지 숨김 경계는 되돌리지 않는다.
9. 앱은 roomId로 방 정보·과거 메시지를 조회하고 STOMP room topic을 구독한다.

## 2. 신청하기

### 2.1 매물 화면에서 신청

1. 사용자가 입주일과 계약 기간을 선택한다.
2. 앱이 기존 `POST /api/v1/listings/{listingId}/bookings`를 호출한다.
3. 기존 Booking Service가 신청을 `REQUESTED`로 저장한다.
4. Booking Service가 같은 트랜잭션에서 재처리 가능한 `BookingCreatedEvent`를 기록한다.
5. 성공 후 앱이 방 보장 API `POST /api/v1/listings/{listingId}/inquiries`를 호출한다.
6. 서버가 문의하기와 같은 비즈니스 키로 방을 보장하고 앱은 반환된 roomId로 이동한다.
7. 서버의 신청 이벤트 handler가 신청 저장 시점에 고정한 매물·신청자·입주 조건·금액 사본으로 같은 방에 `BOOKING_CARD`를 한 번 저장한다.
8. 앱은 메시지 이력에서 신청 카드를 받아 `myRole`에 맞는 화면으로 표시한다. STOMP 단계가 연결되면 같은 카드를 실시간 room topic으로도 받는다.

예약 API가 `BOOKING_ALREADY_EXISTS`를 반환한 경우에도 앱은 기존 신청이 있음을 안내하고 방 보장 API를 호출해 같은 방으로 이동할 수 있다.

정상 화면 흐름에서는 앱이 신청 API 성공 뒤 채팅방 API를 HTTP로 한 번 더 호출해 즉시 이동한다. 두 HTTP 호출 사이에 앱 종료나 네트워크 오류가 생겨도 서버가 저장된 `BookingCreatedEvent`를 자동 처리해 누락된 채팅방과 신청 카드를 보완한다. 이 보상 경로를 위해 앱이 별도의 HTTP 요청을 보낼 필요는 없다.

보상 이벤트는 MySQL에 저장되는 Spring Modulith Event Publication Registry로 유실 없이 관리한다. chat listener는 방을 중복 없이 보장하고, `(chatRoomId, bookingId)`를 기준으로 `BOOKING_CARD`도 한 번만 저장한다. 별도의 `SYSTEM` 메시지와 푸시 알림은 만들지 않는다.

방 보장은 하나의 모드 값으로 분기하지 않고 다음 두 유스케이스로 나눈다.

- **사용자 직접 방 진입**: 사용자가 문의하거나 신청 완료 후 방으로 이동한다. 기존 방을 사용자가 숨겼다면 요청자의 목록에 같은 방을 다시 표시한다.
- **예약 이벤트의 방·카드 보장**: 신청 저장 뒤 서버가 백그라운드에서 누락된 방을 만들고 신청 카드를 한 번 저장한다. 이미 같은 카드가 있으면 아무것도 추가하지 않는다.

구현에서도 사용자 요청은 `ChatService.createInquiry`, 공통 방 보장은 `ChatRoomEnsurer`, 예약 이벤트 카드는 `BookingCardService`로 책임을 나눈다. Booking Service는 이미 조회한 객실 상품과 신청자 공개 뷰를 `BookingCreatedEventFactory`로 조립하므로 chat listener가 신청 뒤 원본 모듈을 다시 조회하지 않는다. 동일 이벤트 재처리는 방·카드·방 재표시를 중복 처리하지 않는다.

### 2.2 채팅 안 신청 버튼

채팅 안 신청 버튼은 백엔드의 새로운 신청 기능이 아니라 기존 신청 화면을 여는 프런트엔드 기능이다.

1. 기존 신청 화면을 연다.
2. 기존 Booking API를 호출한다.
3. 이미 같은 방 안이므로 새 방을 만들지 않는다.
4. 신청 저장 이벤트가 현재 방에 `BOOKING_CARD`를 한 번 추가한다. 앱은 메시지 이력으로 확인하고 STOMP 단계 이후에는 실시간으로도 받는다.

예약 로직을 chat 모듈에 복제하거나 예약 응답에 `chatRoomId`를 추가하지 않는다.

### 2.3 신청 카드 표시

- 서버가 저장하는 카드는 하나이며 임차인과 임대인이 같은 `bookingId`를 본다.
- 임차인은 “신청이 접수되었습니다”와 자신의 신청 내용을 표시한다.
- 임대인은 “새로운 입주 신청이 도착했습니다”와 신청자 상세 내용을 표시한다.
- 카드 값은 Booking Service가 신청 생성 때 이미 조회한 매물·신청자 정보와 상세 조회와 같은 금액 공식을 재사용한다.
- 카드의 고정 라벨은 앱이 `ko/en`으로 표시하고 Google 번역에는 보내지 않는다.
- 동일 `BookingCreatedEvent`가 다시 처리돼도 같은 카드가 두 장 생기지 않는다.

## 3. 실시간 TEXT 메시지와 자동 번역

### 3.1 원문 전송

1. 프런트엔드가 UUID `clientMessageId`를 생성한다.
2. 필요하면 같은 ID로 임시 말풍선을 표시한다.
3. STOMP SEND로 `clientMessageId`와 `content`만 보낸다.
4. 서버가 인증, 채팅방 참여, 차단, UUID, 본문, rate limit을 검사한다.
5. 신규 요청이면 MySQL에 저장하고 방의 마지막 메시지 상태를 갱신한다.
6. 커밋 후 room topic으로 저장 완료 메시지를 발행한다.
7. 발신 session에는 애플리케이션 저장 결과를 보낸다.
8. 프런트엔드는 topic 또는 저장 결과의 `clientMessageId`로 임시 말풍선을 확정한다.

같은 `clientMessageId`의 네트워크 재시도는 새 메시지를 만들거나 방을 다시 발행하지 않는다.

### 3.2 받은 메시지 자동 번역

1. 서버는 원문 저장 성공을 먼저 확정한다.
2. 수신자의 `users.lang`을 번역 대상 언어로 사용한다.
3. Google Cloud Translation이 원문 언어를 감지해 비동기로 번역한다.
4. 서버가 번역본을 별도로 저장하고 수신자에게 번역 결과를 전달한다.
5. 받은 메시지는 번역본을 먼저 표시하고 `원문 보기`로 원문을 확인할 수 있다.
6. 내가 보낸 메시지는 원문을 먼저 표시한다.
7. 원문과 수신 언어가 같거나 번역본이 없으면 원문을 사용한다.

`번역 중`과 같은 대기 화면 문구는 프런트엔드가 결정한다. 백엔드는 원문, 저장된 번역본, 최종 번역 결과만 제공한다. 번역 실패는 이미 성공한 메시지 저장과 전송을 취소하지 않는다.

번역본 옆에는 Google의 표시 요구사항에 맞는 자동 번역 안내를 제공한다. 신고 증거는 화면에 보인 번역본이 아니라 원문을 기준으로 한다.

## 4. 방 목록과 메시지 이력

- 방 목록은 마지막 메시지 시각을 기준으로 최신순이다.
- 빈 방은 생성 시각을 정렬 기준으로 사용한다.
- 메시지는 한 번에 모두 조회하지 않고 `messageId` cursor로 page 조회한다.
- 위로 스크롤할 때는 `cursor`, WebSocket 재연결 보충에는 `afterMessageId`를 사용한다.
- 사용자별 삭제 경계보다 오래된 메시지는 응답하지 않는다.
- 읽음 상태와 `unreadCount`는 계산하지 않는다.
- 받은 마지막 메시지의 현재 언어 번역본이 있으면 방 목록 preview에도 번역본을 사용한다.
- 내가 보낸 마지막 메시지이거나 번역본이 없으면 preview에 원문을 사용한다.
- 마지막 메시지가 `BOOKING_CARD`이면 앱이 `myRole`에 맞는 신청 안내 문구를 preview로 표시한다.

WebSocket은 새 메시지를 즉시 보여 주는 통로이고 REST 메시지 조회는 MySQL에서 확실하게 복구하는 통로다. 둘은 대체 관계가 아니라 함께 사용한다.

## 5. 채팅방 삭제와 새 대화

삭제는 공유 메시지를 즉시 지우는 기능이 아니라 **내 화면에서 방과 이전 이력을 숨기는 기능**이다.

1. 서버가 채팅방과 요청자의 member 상태를 잠근다.
2. 현재 마지막 messageId를 이 사용자의 숨김 경계로 기록한다.
3. 기존 숨김 경계보다 낮아지지 않게 저장한다.
4. 요청자의 채팅방만 목록에서 숨긴다.
5. 상대 member와 상대 화면은 변경하지 않는다.
6. 응답 본문 없이 `204 No Content`를 반환한다.

사용자에게 삭제 취소, 복원 API, 삭제한 채팅방 목록, 내부 삭제 상태를 제공하지 않는다. 삭제한 과거 이력은 사용자 화면에 다시 노출하지 않는다.

같은 숨김 상태에서 DELETE를 반복해도 새 삭제 기록을 만들지 않는다. 숨겨진 동안 실제 새 메시지가 저장되거나 사용자가 직접 다시 문의하면 같은 roomId가 다시 나타날 수 있지만 이것은 삭제 취소가 아니다.

- 이전 삭제 경계 이하: 계속 숨김
- 삭제 이후 실제 새 메시지: 표시
- 직접 문의 또는 새 메시지로 다시 표시돼도 숨김 경계는 유지

중복 `clientMessageId` 재시도와 동일 `bookingId` 이벤트 재처리는 실제 새 활동이 아니므로 방을 다시 표시하지 않는다. 새로 저장된 다른 신청의 `BOOKING_CARD`는 실제 신규 활동이므로 정책에 따라 방을 다시 표시할 수 있다.

현재 구현은 공유 메시지를 물리 파기하지 않는다. 3개월 만료와 양쪽 공통 범위의 물리 삭제는 [후속 고도화 문서](future/02-retention-and-physical-deletion.md)에서 별도로 다룬다.

## 6. 차단

1. 사용자가 채팅방에서 차단을 선택한다.
2. 서버가 방의 두 참여자를 조회한다.
3. JWT 사용자와 다른 참여자를 차단 대상으로 결정한다.
4. 기존 `UserBlockService.block`을 호출한다.
5. 이미 차단한 관계여도 성공한다.
6. 차단 이전 대화와 방은 삭제하지 않는다.
7. 이후 어느 쪽이 보내도 메시지 저장 전에 거부한다.
8. 거부된 본문은 MySQL, broker, 애플리케이션 본문 로그에 남기지 않는다.

차단 해제는 기존 `DELETE /api/v1/users/me/blocks/{userId}`를 사용한다. 차단과 삭제는 별개이므로 과거 기록까지 숨기려면 삭제도 따로 실행해야 한다.

## 7. 채팅방 신고

신고 대상은 개별 메시지가 아니라 채팅방과 그 상대 사용자다.

1. 앱이 고정된 신고 사유 6개를 사용자의 `ko/en` 언어에 맞게 표시한다.
2. 사용자가 사유 한 개를 선택한다.
3. 앱이 `POST /api/v1/chat-rooms/{roomId}/reports`로 reason code 하나만 보낸다.
4. 서버가 방 존재와 신고자의 참여 여부를 확인한다.
5. 서버가 다른 참여자를 신고 대상 사용자로 결정한다.
6. 신고자에게 현재 보이는 마지막 TEXT messageId를 증거 경계로 고정한다.
7. 서버 원문에서 최근 TEXT 최대 20개의 증거 사본을 만든다. `BOOKING_CARD`와 번역문은 제외한다.
8. 신고와 최초 evidence를 한 트랜잭션으로 저장한다.

자유 입력 상세 사유와 사유 목록 조회 API는 만들지 않는다. 신규 접수는 `201`, 같은 방 재요청은 최초 결과와 `200`을 반환하므로 앱은 POST 응답만으로 접수 성공을 확인한다. 신고 접수는 방을 자동 삭제하거나 자동 차단하지 않으며, 사용자가 원하면 신고 후 두 기능을 각각 실행한다.

운영자 검토·최종 처리·신고 자료 만료 정리는 [후속 고도화 문서](future/01-admin-report-management.md)로 분리한다.

### 삭제·차단 상태와 신고

- 정상 방: 현재 보이는 대화 범위 신고 가능
- 숨긴 방: 일반 방 조회에서는 노출하지 않음
- 새 메시지나 직접 문의로 다시 표시된 방: 숨김 경계 이후 대화만 신고 가능
- 차단 상태: 신고 가능
- 이미 저장된 신고 evidence: 이후 사용자가 방을 숨겨도 독립된 신고 자료로 유지

# Project Brief

> 이 문서는 Kohere 프로젝트의 Project Brief다. **MVP 기획 메모**와 **요구사항 정의서**(`docs/requirements/요구사항 정의서 .xlsx`, 2026-06-15 기준)를 반영했다. 요구사항 정의서에도 명시되지 않은 항목은 `(입력 필요)`, 추론으로 채운 항목은 `(확인 필요)`로 표시했다.

## 목적

이 문서는 **외국인 맞춤 주거 유형 탐색 서비스**(Kohere)의 목적·배경·범위·핵심 기능·KPI·마일스톤을 한 곳에 정리해, 합류한 팀원이 프로젝트 맥락을 빠르게 파악하도록 한다. 화면·기능의 상세 명세는 [요구사항 정의서](../requirements/요구사항%20정의서%20.xlsx)를 정본으로 한다.

## 1. 한 줄 요약 (Elevator Pitch)

한국의 주거 형태(고시원·코리빙·쉐어하우스 등)와 부동산 용어를 모르는 **외국인**이, 6단계 진단(지역·입국 목적(유학 여부)·대학 그룹·지역 선택·주거 환경 조건·월세 범위(최소-최대)·ARC 보유 여부)에 답하는 것만으로 **자신에게 맞는 매물을 추천받고(지도 + 리스트), 임대인과 인앱으로 연결**되는 모바일 서비스.

## 2. 배경 (Background / Problem)

### 문제

- 외국인은 한국의 주거 형태 차이(고시원 / 코리빙 / 쉐어하우스 등)와 예산별 선택지를 알기 어렵다.
- 복잡한 한국 부동산 용어가 진입장벽이 되어, 자신의 조건(입국 목적·월세 범위·ARC(외국인등록증) 발급 여부·생활 조건)에 맞는 집을 찾기 힘들다.

### 타겟

고시원 / 코리빙 / 쉐어하우스 등 한국의 주거 형태 차이를 모르고 예산별 선택지를 고민하는 외국인.

### 대표 상황 (페르소나)

1. 입국 1~2개월 전, 해외에서 미리 방을 알아보는 외국인
2. 기숙사에서 주거 변경을 희망하며 임시 거처를 구하는 외국인
3. 이사를 앞둔 외국인

## 3. 목표 (Goals)

### 핵심 가치 (정성 목표)

복잡한 한국 부동산 용어를 몰라도, 몇 가지 질문(지역·입국 목적·주거 환경 조건·월세 범위·ARC)을 통해 자신에게 가장 알맞은 매물 리스트를 추천받을 수 있다.

> (입력 필요) 측정 가능한 목표가 MVP 기획 메모·요구사항 정의서 어디에도 명시되지 않았다. 다음을 정해야 한다.
>
> - 핵심 목표(예: "진단을 완료한 사용자의 N% 이상이 매물 상세 조회 / 신청·문의로 진행")
> - 정량 기준과 달성 시점

## 4. 범위 (Scope)

### In scope (MVP)

요구사항 정의서 기준, MVP는 아래 영역으로 구성된다. (매물 데이터는 **서울 지역 기준**)

| 영역           | 핵심 내용                                                                                                                                                                                                                                                                      |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 인증 · 온보딩 | 소셜 로그인(Apple / Google), 온보딩 필수 정보(이름·성별·생년월일·국가번호·전화번호·비자 정보[유학·연수 / 취업 / 거주·가족동반 / 워킹홀리데이 / 관광 / 기타]), 이용약관·개인정보처리방침 동의, 소셜 로그인 실패 시 에러·재시도 처리. **임대인은 별도 온보딩 트랙**(이름·연락처(SOLAPI SMS 인증) + 외부 비즈노 API로 사업자등록번호 검증, 이메일 미수집)이며 `userType`(세입자/임대인)은 온보딩 단계에서 확정 |
| 홈             | 검색·찜·알림 진입, "유형 진단 시작 / 재진단" 진입(진단 완료 여부로 문구 분기), 최근 본 매물(7일 내, 최대 5개), 진입 시마다 랜덤 퀴즈(정답 여부·오답 해설 즉시 표시, 다국어 번역 제공; ACTIVE 세입자 대상), 생활 팁                                                                                                              |
| 맞춤 진단 챗봇 | 6단계 진단 — ① 지역(서울/부산/경기 선택지 노출,**MVP 데이터는 서울 기준**) ② 입국 목적(유학 / 유학 외, 단일 선택) ③ 대학 그룹·지역 선택(②=유학 → 대학 그룹 6종 중 단일 선택[`HUFS_KHU_KOREA`·`SKKU_SUNGSHIN`·`SNU_CAU_SOONGSIL`·`HONGIK_YONSEI_EWHA`·`KONKUK_SEJONG_HYU`·`ETC`], ②=유학 외 → 지역) ④ 주거 환경 조건(9개 중 최대 3개) ⑤ 월세 최소-최대 범위(듀얼 핸들 슬라이더, `monthlyRentMin`/`monthlyRentMax`) ⑥ ARC 발급 여부 → 결과: 매물 리스트(하단) + 지도(상단) 동시 노출, 0건 시 키워드 조정 제안([ADR-0028](../adr/0028-diagnosis-questions-catalog-store.md)) |
| 매물 탐색      | 지도 탭(학교명·지역명·지하철역 검색, 조건 필터 칩, 클러스터 마커, 지도:리스트 50:50, 추천/가격/거리순 정렬), 매물 상세(사진 갤러리·유형·가격·보증금·계약기간·위치·편의시설 태그·임대인 정보), 찜                                                                      |
| 임대인 연락    | F-03 신청하기(입주 희망일 + 계약기간 1/3/6/12개월) → 신청내역이 인앱 채팅방에 자동 기록(`booking` → `BookingCreatedEvent` → `chat`). 실시간 WebSocket·푸시는 추후, `booking`·`chat` 저장소는 추후 결정([§7](#7-마일스톤-milestones))                              |
| 커뮤니티       | 자유게시판 · 동네생활(제목 + 본문 텍스트 + 사진, 동영상 제외), 좋아요·댓글·공유·신고, 키워드/해시태그 검색, 동네친구 1:1 채팅                                                                                                                                              |

**1차 MVP(2026-07-10) 범위**: 로그인·온보딩 / [Main] 큐레이션 챗봇(F-01, 6단계 진단) / [Main] 맞춤 매물 추천(F-02, 리스트+지도) / 매물 탐색·찜(지도 탭 검색·필터·매물 상세, 찜·최근 본 매물) / 임대인 신청→인앱 채팅 기록(F-03, booking→chat). 커뮤니티는 MVP 이후로 이연. 우선순위·트랙 분담·세부 컷·일정은 [§7 마일스톤](#7-마일스톤-milestones) 참조.

> (작성 중) 더보기 탭(찜한 매물·내 게시글·알림 설정 등)은 요구사항 정의서에서 아직 작성 중이라 **MVP 포함 범위가 미확정**이다. 알림 설정(푸시 on/off 토글)도 정책 논의가 필요하다. `(입력 필요)`

### 주거 환경 조건 9종 (진단 4단계)

즉시 입주 / 여성 전용 / 개인 화장실 / 개인 욕실 / 영어 소통 가능 / 전입신고 가능 / 관리비 없음 / 식사 제공 / 2인실 (영문 라벨 병기)

### Out of scope / 고도화 (MVP 이후)

- 결제 시스템
- 서울 외 지역 매물 수집 (MVP 데이터는 서울 기준)
- 포인트·리워드 시스템 (MVP 범위 밖 — 퀴즈는 학습 피드백만 제공하고 포인트 적립은 없음)
- 임대인 등록 페이지 제휴 또는 자체 생성 (매물 데이터 수급 방식)
- 매물별 리뷰 작성 (결과 정렬이 "리뷰 기반"이나 작성 방식 미정 — 초기엔 추천/가격/거리순 정렬로 제공)
- 메시지 비속어·외부 연락처 유도 필터링 (확정 X)

## 7. 마일스톤 (Milestones)

> 1차 MVP 배포 목표 **2026-07-10(금)** — **단위·통합·E2E 테스트와 최종 점검까지 모두 끝난 상태** 기준. 기준일 2026-06-15(월), 약 4주(영업일 20일). 현재 코드는 **골격 + CI만 존재**(엔티티·엔드포인트 미구현, 영속·보안 스택 도입 전). 인력 **2명** 기준 트랙 분담.

### 1차 MVP 범위 (2026-07-10)

로그인 포함 5개 영역.

1. 로그인 · 온보딩 (소셜 로그인 → JWT)
2. **[Main]** 주거 성향 기반 큐레이션 챗봇 (F-01: 신분 → 위치 → ARC 여부 → 월세 범위(최소-최대) → 기간)
3. **[Main]** 맞춤 매물 추천 (F-02: 리스트 + 지도, 거리·월세 범위 필터)
4. 매물 탐색·찜 (지도 탭 학교명·지역명·지하철역 검색, 조건 필터, 매물 상세, 찜·최근 본 매물)
5. 임대인 신청하기 → 인앱 채팅 기록 (F-03: booking → chat)

②③이 **보호 핵심**. 커뮤니티는 MVP 이후로 이연.

### 영속 배치 (확정 · [ADR-0005](../adr/0005-polyglot-persistence.md))

배치 기준은 **데이터 특성**이며 사람 트랙과 무관하다.

| DB                                    | 모듈                                                           | 근거                                                            |
| ------------------------------------- | -------------------------------------------------------------- | --------------------------------------------------------------- |
| **MongoDB** (Spring Data Mongo) | `listing` + `favorite` + `recent-listing`, `diagnosis` | 지오·가변 스키마 / 문서형 애그리거트·임베드 배열·조인 불필요 |
| **MySQL** (JPA)                 | `auth` · `user`                                           | 계정·토큰 트랜잭션 / 유니크 제약·카운트 정합                  |

→ `community`는 MVP 이후로 이연(MySQL 사용 모듈은 `auth`·`user`만 남는다). **F-03 `booking`·`chat`은 MVP 편입, 저장소 추후 결정(ADR)** — 위 표(확정)에는 넣지 않는다.

→ 모듈 간 직접 조인은 금지라([ADR-0002](../adr/0002-inter-module-communication-via-events.md)) `listing`·`diagnosis`가 같은 Mongo여도 추천은 `RecommendationCriteria` 공개 쿼리로 흐른다(co-location은 부수적).

### 역할 분담 (2명)

트랙은 DB가 아니라 **기능 응집·크리티컬 패스**로 나눈다(두 사람 모두 두 DB를 다룬다). M0에서 인프라 스택을 분담해 셋업하되, **로컬 `docker-compose` 환경(app+MySQL+MongoDB+Redis)은 A+B가 한 번에 공동 구성**한다.

| 트랙      | 개발자 A — 인증·진단 (크리티컬 패스)                                 | 개발자 B — 매물·신청·채팅                                             |
| --------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 모듈      | `auth` · `user` · `diagnosis` · `common`                    | `listing` · 찜 · 지도 · 추천 · `booking`(신청) · `chat`(F-03) |
| 스택      | MySQL(`auth`·`user`) + MongoDB(`diagnosis`)                     | MongoDB(`listing`) + booking·chat 저장소 추후 결정                    |
| 보호 핵심 | M2 진단 챗봇                                                           | M3 매물 추천·지도                                                       |
| 공동      | M0 로컬 컨테이너 환경(docker-compose) · M7 통합·클라우드 이전·배포. |                                                                          |

### 마일스톤

> **개발 전략**: 비용·리스크 사유로 **M0–M4는 전 구간 로컬 컨테이너(docker-compose) 기반으로 개발**(클라우드 인프라 미가동, 비용 0), **M7에서 AWS로 이전·배포**한다. 두 환경은 동일 애플리케이션 Docker 이미지를 쓰되 인프라만 로컬↔매니지드로 바뀐다 — 로컬↔클라우드 구성 대응은 [system-overview §1-3](../architecture/system-overview.md) 참조.

### 크리티컬 패스

**M0-A → M1(auth) → M2(진단) → [추천 criteria 계약] → M3 추천 통합 → M7.** 이 체인이 배포일을 결정한다.

- M0는 1순위 블로커 — JPA/Mongo·Security·`ApiResponse`가 없으면 어떤 모듈도 영속/인증 코드를 못 짠다.
- M1(JWT 사용자 컨텍스트)이 M2~M4의 모든 보호 엔드포인트를 gate한다 → A는 W1 초 SecurityContext stub을 B에게 먼저 넘겨 비차단.
- M2(진단 결과)는 M3(추천)의 선행 조건. M3의 리스트/지도/찜은 진단과 무관해 B가 W1부터 선행 가능.
- M4(신청·채팅 F-03)는 M1(`auth` 사용자 컨텍스트)·M3(`listing`)에 의존한다 — 둘이 끝나야 신청→채팅 기록을 붙인다.
- 연동 계약(병렬 전제): ① 인증 컨텍스트(A→B, W1 1일차) ② 추천 `RecommendationCriteria`(A↔B, W2 시작, [ADR-0002](../adr/0002-inter-module-communication-via-events.md) 공개 쿼리) ③ 신청→채팅 이벤트 `BookingCreatedEvent`(`booking`→`chat`, [ADR-0002](../adr/0002-inter-module-communication-via-events.md) 도메인 이벤트).

### 스코프 컷 / 지금 결정할 것

- **M5(커뮤니티)는 1차 MVP에서 이연 확정**(삭제 아님, MVP 이후). 1차 범위는 로그인 + F-01(진단)·F-02(추천)·F-03(신청→채팅)뿐. 7/7 feature freeze 후 **7/8–7/10 통합·전체 테스트·하드닝·검증**을 풀가동(테스트·점검이 데드라인의 일부). 보호 핵심(M2·M3)은 6/30–7/2 완료를 내부 데드라인으로 앞에 끝내고, 지연 시 버퍼로 흡수.
- **결정 완료:**
  1. 임대인 연락 = **인앱 채팅(F-03: 신청→채팅 기록) 채택** — 외부 메신저 링크·전화 방식은 종료. 단 실시간 메시징(WebSocket)·푸시는 추후.
  2. MySQL 마이그레이션 도구 = Flyway 유지.
  3. MongoDB 마이그레이션 도구 = **Mongock**(`@ChangeUnit`, 모듈별) 채택([ADR-0032](../adr/0032-mongodb-migration-runner.md)).
- 확정 컷: 추천은 규칙기반(ML 제외), OAuth는 Google 먼저(Apple 여유 시). 지도는 Mongo 지오로 bbox 기반 마커 조회와 거리순을 유지하고, 클러스터링은 프론트 지도 SDK가 담당한다. (커뮤니티 사진 업로드는 community 이연으로 범위 밖.)

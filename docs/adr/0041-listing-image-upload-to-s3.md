## Status

Proposed · **Amended(수정 요청의 혼합 키 허용 · 확정본 삭제 시점, 2026-08-23)**

> **Amended — 매물 수정 요청은 임시 키와 기존 확정 키를 섞어 받고, 참조를 잃은 확정본은 저장이 성공한 뒤에 지운다.**
>
> 본 ADR은 **등록**만 다뤘다. 등록 요청의 `imageKeys`·`roomOffers[].roomImageKeys`에는 임시 키(`uploads/{landlordId}/…`)만 올 수 있었고, 확정본(`listings/…`)은 한 번 만들어지면 삭제 대상이 아니었다 — §4가 규정한 보상 삭제는 **이번에 만든 복사본**을 걷어내는 것뿐이다. 임대인 매물 수정(`PUT /api/v2/listings/{listingId}`, [03-listings-favorites](../api/specs/03-listings-favorites.md))이 생기면서 두 전제가 모두 성립하지 않는다 — 수정은 **사진 대부분을 그대로 두고 일부만 바꾸는** 요청이고, 바뀐 자리의 옛 확정본은 저장되는 순간부터 아무도 참조하지 않는다.
>
> **① 수정 요청은 두 종류의 키를 섞어 받는다.** 한 배열 안에 임시 키와 **그 매물의 기존 확정 키**가 함께 올 수 있다. 임시 키는 §4대로 확정 위치로 복사하고, 확정 키는 **복사 없이 그 자리에 유지**한다. 안 바꾼 사진까지 전부 다시 올리게 하는 대안은 임대인에게 부당하고 같은 파일을 S3에 두 벌 만든다. §2의 "확정 키는 새 UUID를 뽑지 않고 임시 키의 파일명을 그대로 옮긴다"가 여기서 값을 한다 — 재확정이 같은 파일명으로 떨어져도 충돌하지 않는다.
>
> **② 확정 키는 「그 자리에서 온 것」만 허용한다.** 확정 키는 경로에 역할이 이미 박혀 있으므로(`listings/{listingId}/cover/…` vs `listings/{listingId}/rooms/{roomOfferId}/…`) **요청 JSON에서 놓인 자리와 일치해야 한다.** 서버는 수정 전 문서에서 자리별 허용 집합(커버 1개 + 방마다 1개)을 만들어 대조하고 어긋나면 `400`이다 — 커버↔방·방↔방 교차는 금지이며, `roomOfferId`가 `null`인 **신규 방은 임시 키만** 쓸 수 있다(확정 키가 담아야 할 id가 아직 발급되지 않았다). 이 **멤버십 대조가 소유권 검사를 겸한다** — 남의 매물 확정 키는 어느 집합에도 없어 S3를 부르기 전에 걸린다(§2에서 임시 키의 `landlordId` 세그먼트가 하던 역할과 같다). 대가로 **방 사진을 대표 사진으로 승격하려면 다시 올려야** 하지만, 저장 경로가 역할을 거짓말하지 않는 쪽을 택한다.
>
> **③ 참조를 잃은 확정본은 저장이 성공한 뒤에 지운다.** 대상은 저장 직후 산정하는 **`OLD − NEW`** — 수정 전 문서에서 파생한 확정 키 집합에서 저장된 문서의 확정 키 집합을 뺀 차집합이며, 커버와 **모든 방**(비활성 방·요청에서 빠져 보존된 방 포함)을 함께 훑는다. 그 방들의 사진은 문서에 남아 `NEW`에 들어가므로 지워지지 않고, 방을 되살리면 사진도 함께 살아난다.
>
> **저장 *전에* 지우는 안은 어느 경우에도 없다.** 검증이나 저장이 실패하면 **공개 중인 매물의 사진이 사라지기** 때문이고, 이는 §4가 "복사 → 저장 → 실패 시 복사본만 되돌리기"로 못박은 것과 같은 이유다. 저장이 실패하면 이번에 복사한 것만 걷어내고 옛 키는 건드리지 않으며, 저장이 상태 불일치로 거절되면 문서가 바뀌지 않았으므로 **아무것도 지우지 않는다.**
>
> **삭제는 best-effort다.** `uploads/`의 임시본을 지울 때와 같은 계약이라(예외를 던지지 않고 로그만 남긴다) 원래 흐름을 막지 않는다. 실패한 만큼 고아가 남고 재시도하지 않는데, §3의 만료 규칙이 `uploads/` 전용이라 **`listings/` 아래에서는 이 삭제가 유일한 회수 경로**다. 그래서 아래 Consequences의 후속 작업 「정리 배치」는 여전히 유효하고, 대상 산정 시 **비활성 방의 사진까지 참조로 세어야 한다** — 참조는 남아 있으나 어떤 요청도 그 사진을 되짚지 않는다.
>
> **`listings/` 전체에 만료 규칙을 거는 안은 어느 경우에도 없다** — 살아 있는 사진까지 지운다. §3이 prefix로 상태를 가른 설계가 그 실수를 구조적으로 막고 있으므로 여기서도 유지한다.
>
> **§1·§2·§3·§5·§6은 그대로 유효하다.** §4의 순서도 **등록 경로에서는 그대로**이고, 수정 경로의 순서는 「키 검증 → 확정 복사 → 저장 → (성공) 임시본 삭제 + `OLD − NEW` 삭제 / (실패) 복사본 되돌리기」다. 이 개정의 코드 주장은 `feature/267-landlord-listing-update` 기준이며, 헤더의 기준 코드는 **작성 시점** 앵커다.

## Context

- 이슈 #220의 인수 조건은 "임대인이 매물을 등록할 때 **필요한 정보/이미지를 입력하면 DB와 S3에 매물이 저장된다**"인데, 개편 전 `POST /api/v2/listings`는 이미지를 **URL 문자열**(`imageUrls`·`roomOffers[].roomImageUrls`)로 받았다. 그 URL을 만들어 주는 주체가 없어 인수 조건이 채워지지 않았다.
- **클라이언트는 브라우저**이고, 확정된 등록 화면은 **파일마다 진행률·전송 속도·개별 재시도**를 보여준다. 이 요구가 요청 구조를 결정한다 — 파일을 한 요청에 몰아 실으면 브라우저가 주는 진행 이벤트는 요청 전체 하나뿐이라(`XMLHttpRequest.upload` 의 `loaded`/`total`) 파일별 진행률을 만들 수 없고, 실패한 파일만 다시 올리는 것도 불가능하다.
- **사진은 줄이지 않고 원본 그대로 올라온다.** 폰 사진은 12MP에서 3~5MB, 48MP에서 8~15MB다. `roomOffers`에 개수 상한이 없어 한 매물이 실을 수 있는 총량에도 상한이 없다.
- 이슈는 **프론트가 S3에 직접 올리는 방식을 기각**했다 — "S3가 listingId로 구분되어 있으므로 매물 정보를 등록하기 전에는 listingId를 알 수 없다. 매물 정보를 따로, 이미지를 따로 등록할 경우에는 정합성 불일치 상태가 발생할 수 있다."
- **인프라는 이미 있다.** `infra/terraform/modules/shared/s3-cloudfront`가 비공개 S3 버킷 + CloudFront(OAC)를 정의하고, dev·prod IAM이 앱 역할에 `PutObject`·`GetObject`·`DeleteObject`·`ListBucket`을 부여하며, 앱 환경변수 `APP_IMAGES_BUCKET`·`APP_IMAGES_CDN_DOMAIN`까지 주입된다. 모듈 주석이 설계를 못 박아 두었다 — "도메인은 **키 프리픽스로 구분**", "읽기는 CloudFront 직결".
- 같은 버킷을 **생활팁 이미지**가 `life-tips/` prefix로 이미 쓰고 있다. 국기는 이 버킷이 아니라 외부 `flagcdn.com`이다.
- 등록 페이지는 API와 **같은 도메인**이라 CORS 문제가 없다.
- 두 저장소(S3·MongoDB)에 걸친 쓰기라 **분산 트랜잭션이 없다.**

## Decision

**사진은 한 장씩 별도 API로 받아 임시 위치에 두고, 등록 요청은 그 키 목록만 참조한다. 등록이 확정될 때 사진을 확정 위치로 복사한다.**

### 1. 두 단계로 나눈다

| 단계 | 엔드포인트 | Content-Type | 횟수 |
|---|---|---|---|
| 업로드 | `POST /api/v2/listings/images` | `multipart/form-data`(파일 1개) | 파일 수만큼 |
| 등록 | `POST /api/v2/listings` | `application/json` | 1회 |

업로드 응답은 `{ key, url }`이다. **`url`은 폼에서 미리보기로 띄우는 값, `key`는 등록할 때 되돌려 보내는 값**이다.

요청이 파일마다 갈리므로 진행률·속도·재시도가 파일 단위로 성립한다. 등록 요청은 다시 JSON이 되어 **Swagger 요청 스키마도 복구된다** — 단일 multipart일 때는 `restdocs-api-spec`이 파일 part를 표현하지 못해 문서가 반쪽이었다.

**사진과 방의 짝은 JSON 구조가 표현한다** — 커버는 `imageKeys`, 방은 `roomOffers[].roomImageKeys`다. part 이름에 인덱스를 박아 넣던 방식(`roomImages0`)이 사라진다.

장수는 **필드당 최대 5장**이다(커버 1~5, 방마다 2~5 — 최소 2장은 v4 저장 불변식이다). 장당 **10MB**, 형식은 `image/jpeg` · `image/png` · `image/webp` · `image/heic`이며 HEIC는 **변환하지 않고 저장만** 한다.

### 2. 키가 두 벌이다 — 임시와 확정

```
uploads/{landlordId}/{uuid}.{ext}                         ← 업로드 시점(listingId를 아직 모른다)
listings/{listingId}/cover/{uuid}.{ext}                   ← 등록 확정
listings/{listingId}/rooms/{roomOfferId}/{uuid}.{ext}
```

**확정 키는 새 UUID를 뽑지 않는다.** 임시 키의 파일명(`{uuid}.{ext}`)을 그대로 옮겨 붙인다 — 확장자를 다시 만들지 않으므로 업로드 때 검증한 형식과 확정 키의 확장자가 어긋날 수 없다.

버킷을 새로 만들지 않는다. 모듈 설계대로 도메인을 키 prefix로 가른다(생활팁은 `life-tips/`).

**임시 키에 `landlordId`를 박는 것이 소유권 검사다.** 등록 요청이 남의 `uploads/{다른 id}/…`를 가리키면 문자열 비교만으로 걸러진다 — S3를 부르기 전에 막힌다. 이게 없으면 남이 올린 사진을 자기 매물에 붙일 수 있다.

**저장하는 URL은 CloudFront 도메인 기준이다** — `https://{APP_IMAGES_CDN_DOMAIN}/{key}`. 버킷이 비공개(OAC)라 S3 URL로는 읽히지 않는다. 쓰기는 `APP_IMAGES_BUCKET`으로, 읽기 URL은 `APP_IMAGES_CDN_DOMAIN`으로 — 같은 객체를 두 경로로 가리킨다.

### 3. 고아를 prefix로 가른다

사진이 매물보다 **먼저** 저장되므로, 사용자가 사진만 올리고 폼을 버리면 파일이 남는다. 이전 설계에서 고아는 겹사고에만 생기는 예외였지만 **이제는 일상**이다.

**임시 prefix에만 만료 규칙을 건다** — `uploads/` 아래는 7일 뒤 삭제한다. prefix가 갈리므로 **살아 있는 매물 사진(`listings/`)은 이 규칙에 걸릴 수가 없다.** 초안이 태그(`pending=true`) 기반 만료를 기각한 이유가 여기서 해소된다 — 태그 방식은 태그 제거가 실패하면 살아 있는 사진을 지웠지만, prefix는 객체가 어디에 있느냐가 곧 상태라 뒤집힐 여지가 없다.

7일로 두는 이유는 임대인이 며칠에 걸쳐 폼을 작성해도 사진이 남아 있어야 하기 때문이다. 버려진 파일이 일주일 쌓여도 저장 비용은 무시할 수준이다.

### 4. 등록 순서와 보상

```
장수 검사 → 키 소유권 검사 → 나머지 등록 검증
  → 식별자 선발급 → 확정 위치로 복사 → 문서 저장 → 임시본 삭제
```

- **존재 확인을 따로 하지 않는다.** 없는 키는 복사가 알려준다 — MinIO로 실측한 결과 원본이 없는 `CopyObject`는 `NoSuchKeyException`(404 `NoSuchKey`)으로 오고, 복사는 대상의 `Content-Type`도 그대로 보존한다. 미리 물어봐서 얻을 정보가 없다. 게다가 확인과 복사 사이에 만료가 걸릴 수 있어 **복사 실패 경로는 어차피 있어야 한다** — 선검사는 그 경로를 없애 주지 못하고 파일 수만큼 왕복만 늘린다.
- **`NoSuchKey`만 사용자 오류(400)로 가른다.** 나머지 저장소 실패는 `502 UPSTREAM_ERROR`다. 이 구분이 없으면 잘못된 키를 보낸 요청이 "서버 장애니 재시도하라"는 502를 받고, 재시도해도 영원히 실패한다.
- **임시본은 실패해도 지우지 않는다.** 복사나 저장이 실패하면 **복사본만** 걷어내고 `uploads/`의 원본은 남긴다 — 사용자가 다시 제출하면 같은 키를 그대로 쓸 수 있고, 안 하면 7일 뒤 만료가 치운다. 보상 실패에도 안전망이 있는 구조다.
- 여러 장 중 하나가 잘못되면 앞의 것이 이미 복사된 상태로 실패한다. 그 복사본은 보상 삭제가 걷어낸다 — 저장 실패 경로와 같은 코드라 새로 늘지 않는다.

식별자를 저장 전에 발급하는 이유는 확정 키가 `listingId`·`roomOfferId`를 포함하기 때문이다. 저장 기술이 식별자 형식을 정하므로 발급도 저장소(`ListingRepository.nextIdentity()`)가 맡는다.

### 5. 버저닝을 끈다

버킷은 `enable_versioning` 기본값이 `true`였다. 켜진 상태에서는 `DeleteObject`가 삭제 마커만 남기고 이전 버전이 그대로 과금돼 **보상 삭제도 만료 규칙도 실제로 지우지 못한다.** 이미지는 덮어쓸 일이 없고 되돌릴 필요도 없으므로 끈다. 같은 버킷을 쓰는 생활팁도 같은 판단이다.

라이프사이클에는 **미완료 멀티파트 정리**(`abort_incomplete_multipart_upload`, 7일)도 함께 둔다. 지금은 10MB 단일 `PutObject`라 발동하지 않지만, 제한을 올리거나 `S3TransferManager`로 바꾸면 조각이 쌓이는데 `ListObjects`에 보이지 않아 아무도 눈치채지 못한다.

### 6. 포트·어댑터

`listing/domain/image/ListingImageStorage`(포트)와 `listing/infrastructure/external/s3/S3ListingImageStorage`(어댑터)로 나눈다 — `PlaceSearchClient`·`BusinessRegistryVerifier`와 같은 구조다(도메인은 포트만 알고 SDK는 인프라에 가둔다).

로컬은 **MinIO**를 쓴다. S3 API 호환이라 **같은 어댑터에 endpoint만 바꿔** 붙인다 — 별도 스텁 구현을 만들지 않는다. 로컬에서도 실제 업로드 경로를 그대로 태우므로 "로컬만 통과"가 생기지 않는다. 저장소를 띄우지 않는 환경(test)만 `app.images.enabled=false`로 스텁 폴백을 쓴다.

## Alternatives

| 대안 | 장점 | 단점 | 채택 안 한 이유 |
|---|---|---|---|
| **A. 단일 multipart 요청**(초안에서 채택했다 기각) | 요청 한 번으로 끝나 정합성 창이 가장 좁고 고아가 예외로만 생긴다 | 브라우저가 요청 단위로만 진행률을 주고, 요청 총량에 상한이 걸린다 | **기각.** 확정된 UI가 파일별 진행률·재시도를 요구하는데 구조상 만들 수 없다. 더해 원본 사진 기준 방 타입 3개면 이미 `max-request-size`를 넘고, 그 실패는 서블릿이 핸들러 전에 끊어 **어느 파일이 문제인지 못 알린 채** 전부 올린 뒤에 난다 |
| **B′. 파일별 업로드 API(채택)** | 진행률·재시도가 파일 단위. 형식·크기 검증이 **업로드 전**에 남고 버킷 CORS도 필요 없다. 등록이 JSON으로 돌아와 Swagger가 복구된다 | 서버가 받았다 다시 올리는 왕복이 있다. 고아가 일상이 된다 | **채택** |
| B. presigned URL | 서버 대역폭 0. 전송이 한 번뿐이라 원본 사진에 가장 강하다 | 크기 상한을 걸 수단(`content-length-range`)이 Java SDK v2에 없어 검증이 **업로드 후**로 밀린다. 브라우저면 버킷 CORS가 필요하고 URL 수명·권한을 따로 관리해야 한다 | 미채택 — 검증을 앞에 두는 편이 낫고, 축소를 넣으면 대역폭 이점이 사라진다 |
| C. 등록 후 별도 이미지 API | 각 요청이 단순하다 | 등록 직후 사진 없는 매물이 존재하는 창이 생긴다 | 미채택 — 사진 없는 매물을 관리자·통계가 보게 된다 |
| D. 프론트가 S3에 직접 전송(키도 프론트가 결정) | 서버가 파일을 다루지 않는다 | 키를 신뢰할 수 없어 남의 영역에 쓸 수 있다 | 미채택 — **이슈가 이미 기각**했다 |

## Consequences

- **긍정**: 인수 조건이 채워진다. 확정된 UI를 그대로 만들 수 있다. 이미 깔려 있던 버킷·CDN·IAM·환경변수를 그대로 쓰므로 인프라 추가가 만료 규칙 하나뿐이다. 등록이 JSON이라 Swagger 요청 스키마가 정상으로 돌아온다. 로컬도 MinIO로 실제 코드 경로를 검증한다.
- **부정/트레이드오프**
  - **요청이 1회에서 N+1회로 는다.** 클라이언트가 부분 성공·재시도를 다뤄야 한다.
  - **서버가 파일 바이트를 다루고, 받았다 다시 올린다.** 총 전송량이 2배다. 업로드 전 축소를 넣으면 무의미해지는 비용이지만 지금은 축소가 없다.
  - **고아가 일상이 된다.** 만료 규칙이 없으면 버려진 파일이 무한히 쌓인다 — 규칙이 이 설계의 필수 부품이지 위생 장치가 아니다.
  - **업로드와 등록 사이에 7일 시한이 생긴다.** 넘기면 사진을 다시 올려야 한다.
  - **임시 사진이 CDN URL로 열린다.** 키가 UUID라 추측은 어렵지만, URL을 아는 사람은 등록 전 사진을 볼 수 있다. 미리보기를 단순하게 유지하려고 수용한다.
  - **`listings/` 아래 고아는 만료가 없다.** 복사까지 성공한 뒤 저장과 보상 삭제가 **둘 다** 실패하면 남는다. 드물지만 정리 배치 없이는 영구히 남는다.
  - **버저닝을 끄면 실수로 덮어쓴 이미지를 되돌릴 수 없다.** 생활팁 이미지에도 적용된다.
- **후속 작업**
  - `listings/` 키와 MongoDB를 대조하는 **정리 배치**. 실제 상태를 비교하므로 살아 있는 사진을 지울 위험이 없다.
  - 업로드 전 **클라이언트 축소**. 총 전송량·CDN 비용·조회 체감을 한꺼번에 줄이는 유일한 수단이다.
  - HEIC 변환이 필요해지면 별도로 다룬다(지금은 저장만).
  - S3가 한 번 켠 버저닝은 `Suspended`만 되고 **기존 버전은 남는다** — 이미 배포된 환경은 일회성 정리가 필요하다.

## Validation

- 업로드 API에 파일 한 장을 보내면 `{ key, url }`을 받고, 그 `key`가 `uploads/{내 landlordId}/…` 형태이며 `url`을 열면 그 사진이 보인다.
- 형식·크기·빈 파일 위반은 업로드 API에서 각각 `415`·`413`·`400`이고 **저장소에 아무것도 올라가지 않는다**.
- 등록 요청이 남의 `uploads/{다른 id}/…` 키나 없는 키를 가리키면 `400`이고 **매물이 만들어지지 않는다**.
- 등록에 성공하면 응답 URL이 `https://{cdn}/listings/{listingId}/…` 형태이고, 그 키로 객체가 실제로 존재하며, **`uploads/`의 임시본은 사라진다**.
- 매물 저장이 실패하면 복사본이 남지 않고 **임시본은 그대로 남는다** — 목으로 검증한다.
- 로컬에서 MinIO를 띄우고 `http/listing.http`로 업로드 → 등록을 순서대로 실행하면 버킷의 객체가 `uploads/`에서 `listings/`로 옮겨 간다.

# ADR-0009. 서버 JWT 서명은 HS256으로 한다 (MSA 분해·외부 검증자 도입 시 RS256/ES256+JWKS로 전환)

## Status

Accepted

> [ADR-0003](./0003-jwt-auth-after-oauth-login.md)은 access를 무상태 JWT로 정하면서 **서명 알고리즘을 미결**로 남겼다(0003 §후속 L69: 대칭 HS256 vs 비대칭 RS256/ES256 → 별도 ADR). 본 ADR이 그 후속을 닫는다 — **현재는 HS256**, 그리고 **전환 트리거**(검증이 신뢰 경계를 넘는 시점)를 미리 박아둔다.

## Context

- **자체 access 토큰 모델**([ADR-0003](./0003-jwt-auth-after-oauth-login.md)): 소셜 OIDC 로그인 1회 검증 후 서버가 자체 JWT(access)를 발급, 매 요청은 **서명·만료만** 검증(무상태). refresh는 불투명 토큰이라 서명 무관([ADR-0006](./0006-refresh-token-store-redis.md)).
- **현재 아키텍처는 모듈러 모놀리식**([ADR-0001](./0001-bounded-context-module-decomposition.md)) = **단일 프로세스·단일 배포**. 토큰을 발급하는 `auth`와 검증하는 공통 보안 필터(`JwtAuthenticationFilter`, `common`)가 **같은 신뢰 경계** 안에 있다.
- 핵심 원리: 비대칭 서명(RS256/ES256)이 필요한 트리거는 **"검증이 신뢰 경계를 넘는가"**(발급을 신뢰하지 않는·위조 권한을 줘선 안 되는 검증자가 생기는가)이지, **서비스 개수가 아니다.**
  - **HS256(대칭)**: 검증키 = 서명키(같은 시크릿). 시크릿을 가진 쪽은 검증도 하고 **위조도 한다.**
  - **RS256/ES256(비대칭)**: 발급자만 **개인키로 서명**, 검증자는 **공개키로 검증만**(위조 불가).
- 이미 **외부 발급자 검증**에 비대칭 패턴을 쓰고 있다: 소셜 OIDC(Google/Apple)가 자기 **개인키로 `idToken` 서명**(RS256/ES256), 우리는 **공개키(JWKS)로 검증만**(Nimbus `JwtDecoder`, [system-overview §3-3](../architecture/system-overview.md)) — 우리는 Google 토큰을 위조 못 한다. 내부 RS256은 `auth`가 "내부의 Google"이 되는 동일 구조다.
- 따라서 "지금" 알고리즘과 "언제 바꿀지"를 함께 정해야 한다.

## Decision

**서버 자체 access 토큰 서명은 HS256(HMAC-SHA256, 대칭)으로 한다.** jjwt(`io.jsonwebtoken`) + 시크릿은 코드에 박지 않고 **런타임 주입**(env/AWS Secrets Manager, [ADR-0003](./0003-jwt-auth-after-oauth-login.md) 키 관리).

세부 정책:

1. **근거 — 단일 신뢰 경계**: 발급(`auth`)과 검증(`common` 필터)이 같은 프로세스·배포에 있어 시크릿이 **한 경계 안에만** 머문다. 이 경우 "검증키=서명키"인 HS256이 안전하고, 키쌍·JWKS·공개키 캐시 같은 운영 부담이 없다.
2. **수평 확장과 무관**: access 무상태라 인스턴스를 N개로 확장해도([ADR-0003](./0003-jwt-auth-after-oauth-login.md)) **같은 배포·같은 시크릿이면 여전히 단일 신뢰 경계** → HS256 유지(인스턴스 수는 트리거가 아니다).
3. **`common` 공유 ≠ 키 공유**: `common`은 **검증 코드/메커니즘**(필터)만 공유한다. **키(시크릿/공개키)는 코드가 아니라 런타임 주입**이다. 같은 `common`을 써도 서명 능력은 시크릿을 받은 쪽에만 생긴다.
4. **시크릿 위생**: 충분한 길이의 무작위 시크릿, **신뢰 경계 밖으로 절대 반출 금지**, 회전 절차 마련([ADR-0003](./0003-jwt-auth-after-oauth-login.md) 후속/키 관리).
5. **전환 트리거 (미리 명시)** — 다음 중 하나가 발생하면 **RS256/ES256 + JWKS**로 전환한다:
   - (a) 진짜 **MSA로 분해**되어 `listing`·`booking`·`chat`… 각 서비스가 **토큰을 자체 검증**(내부 zero-trust/defense-in-depth)하게 됨, 또는
   - (b) `auth` 발급을 신뢰하지 않는 **외부/서드파티 검증자**가 토큰을 검증해야 함.
   - **전환 모델**: `auth`만 **개인키로 서명**(개인키는 `auth` 밖으로 유출 금지), 나머지·외부는 **공개키만** `auth`의 **JWKS 엔드포인트**에서 받아 캐시해 **검증만** 한다. `common` 필터는 검증 코드를 공유할 뿐 서명키를 공유하지 않는다(서명 권한은 `auth` 한 곳).
6. **예외 — 게이트웨이 검증 독점**: MSA여도 **API 게이트웨이가 입구에서 검증을 종료**하고 내부 서비스는 게이트웨이를 신뢰(자체 검증 안 함)하면, 시크릿이 **한 곳(게이트웨이)** 에만 머무르므로 HS256도 성립한다. 즉 기준은 **"발급을 신뢰 안 하는 검증자가 몇 곳 생기느냐"**다.

## Alternatives

| 대안 | 장점 | 단점 | 채택 |
|---|---|---|---|
| **A. HS256 (채택, 현 단계)** | 단순·빠름, 키 1개, 단일 신뢰 경계에 적합, JWKS·키쌍 운영 불필요 | 검증키=서명키 → **신뢰 경계 밖 검증자에 주면 위조 권한까지 넘어감** | **현재 단일 경계라 단점 미발현 → 채택** |
| **B. RS256/ES256 + JWKS** | 검증자에 공개키만 → **위조 불가**, 다수·외부 검증자 안전, OIDC와 동일 패턴 | 키쌍·JWKS 엔드포인트·공개키 캐시·키 회전 운영 | **전환 목표**(트리거 발생 시) |
| **C. 지금부터 RS256 선제 도입** | 미래 전환 비용 0 | 현 모놀리식엔 JWKS·키 회전 **운영 오버헤드만**(이득 없음) | YAGNI — 트리거 시 전환이 합리 |

## Consequences

- **긍정**
  - **단순·가벼움**: 키 1개(시크릿 주입), JWKS·공개키 배포 인프라 불필요. 수평 확장과 무관.
  - 전환 경로가 ADR로 **닫힘**: "언제 RS256으로 가는가"가 트리거로 문서화됨.
- **부정/트레이드오프**
  - 시크릿이 **발급·검증 공용**이라 신뢰 경계 밖으로 새면 곧 위조 권한 유출 → **MSA 분해/외부 검증자 도입 시 즉시 RS256 전환 필수**.
  - HS256 시크릿 **강도·회전** 규율 필요.
- **후속 작업**
  - [build.gradle](../../build.gradle) jjwt 추가 시 HS256 서명/검증 배선. 시크릿 길이·회전 절차 확정([ADR-0003](./0003-jwt-auth-after-oauth-login.md) 후속).
  - [system-overview §3-3](../architecture/system-overview.md) 서버 JWT 서명 항목 갱신(✅ 본 결정).
  - **아키텍처 변경(서비스 분해/외부 검증자) 리뷰 시 트리거 점검** → RS256/ES256+JWKS 전환 ADR.

## Validation

- **단일 신뢰 경계 유지 확인**: 서명 시크릿이 발급·검증 동일 배포에만 주입되고 **신뢰 경계 밖으로 나가지 않는지** 점검.
- **전환 트리거 점검**: 서비스 분해·외부 검증자 도입 설계/PR에서 RS256+JWKS 전환을 **필수 체크리스트**로.
- **재검토 시점**: 위 트리거 (a)/(b) 발생 즉시(검증이 신뢰 경계를 넘는 순간).

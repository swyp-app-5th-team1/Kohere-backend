## Status

Proposed

> 기존 v1 진단 질의응답([ADR-0028](./0028-diagnosis-questions-catalog-store.md): `GET /questions/{step}` + `POST /answers` + `POST /diagnoses`, 클라이언트가 `step`·확정 시점을 주도)은 그대로 둔다. 본 ADR은 issue #157의 요구(지역 매물 부재 시 재질의·종료, step 대신 서버 주도 next, 서버 자동 확정, 조정 제안 제거)를 **하위 호환이 깨지는 변경**으로 보고 `/api/v2`에 새 흐름으로 신설하는 결정이다.
>
> **서버가 주도하는 것은 질문과 분기까지다.** 진단 **시작**(`POST /start`)과 확정 후 **매물 조회 시점**(v1 `GET /diagnoses/{id}/recommendations`)은 클라이언트가 결정한다 — 서버는 결과코드로 "다음에 할 일"만 알린다.

## Context

- issue #157 재정의 요구: (1) ① 지역 답 직후 매칭 매물이 0건이면 "다른 지역 방을 찾아보시겠어요?"를 묻고 "예" → 다른 지역으로 재시도 / "아니오" → **진단 챗봇 종료(종료코드 반환)**. (2) 클라이언트가 `step`을 지정하는 방식이 비효율적이라 **"next"만 요청하면 서버가 맞는 질문을 반환**하고, 언제 확정할지도 **서버가 판단**한다(빌더 완성 시 자동 확정, 지역 예외질문도 서버가 판단). (3) 추천 0건 시 조정 제안(`suggestions`)은 불필요 — 6단계까지 마친 뒤 매칭이 없으면 **`NO_MATCH` 코드만** 반환. (4) **기존 v1 로직은 건드리지 않고 API 버전을 올려** 구현한다.
- **주도권 경계 재정의(#157 후속 피드백)** — 위 요구2의 "서버 주도"는 **질문·분기까지**이지 흐름 전체가 아니다: (5) **필터링된 매물을 언제 요청할지는 클라이언트가 정한다** — 확정 응답에 추천 목록을 인라인으로 실어 보내지 않고 `diagnosisId`만 준다(클라가 v1 추천 엔드포인트로 별도 요청). 단 **① 지역만은 예외적으로 서버가 미리 필터링**한다(0건이면 끝까지 진행시키는 게 낭비이므로 — 이때도 목록이 아니라 존재 유무만 본다). (6) **예외질문("다른 지역 방을 찾아보시겠어요?")도 채팅 질문의 일부**다 — 서버 합성 문구나 `suggestions` 기계로 따로 관리하지 말고 **문항 카탈로그의 일반 question**으로 두고 `NEXT_QUESTION`으로 내려보낸다. 그 예/아니오 응답에만 **클라이언트가 행할 행위를 코드(재시도/진단종료)로** 알린다. (7) **진단 시작도 클라이언트가 주도한다** — 진단을 하다 홈으로 나갔다 다시 시작하면 **언제나 처음부터**여야 하고, 그 상황에서 서버가 남아 있는 기존 진행 정보를 보고 이어가면 안 된다.
- 배선 사실(코드 확인): `/api/v1`은 전역 설정(`context-path`/`servlet.path`/`WebMvcConfigurer` PathPrefix)이 아니라 **각 컨트롤러의 `@RequestMapping("/api/v1/...")` 리터럴**이다. `SecurityConfig`의 `.anyRequest().authenticated()`가 `/api/v2/**`를 자동으로 인증 대상에 포섭한다. 따라서 **새 컨트롤러 하나를 추가**하면 v1 파일·보안 설정 변경 없이 `/api/v2`가 붙는다([api-design-guide](../api/api-design-guide.md): "하위 호환이 깨지는 변경은 `/api/v2`로 올린다").
- v1 진단 도메인 사실(코드 확인): (a) 진행 중 답은 `diagnoses` 컬렉션의 IN_PROGRESS 초안(사용자당 1건)에 저장되고 `Diagnosis` 애그리거트에는 **진행 커서가 없다**. (b) `validateComplete`는 `region`·`purpose`·(목적 분기)`university`/`district`·`monthlyRentMin/Max`·`arcStatus`만 필수로 보고 **`conditions`(④)는 필수가 아니다**(비어도 통과). (c) ⑥ `arcStatus=NO_ARC`는 파생 조건 `NO_ARC`를 `conditions`에 교차 기록하고, 초안 시작 시 `conditions`가 빈 집합으로 초기화된다. → **"답 필드 null 여부"로 진행 위치·완료를 추론하는 것은 불안정**하다(④를 건너뛰거나 오판).
- 매칭 경로 사실: 매물 조회는 `listing`의 공개 query `recommendByCriteria`(동기)뿐이다 — `diagnosis → listing::api` 의존은 이미 화이트리스트되어 있고, 즉시 결과가 필요한 조회는 이벤트가 아니라 동기 공개 query다([ADR-0002](./0002-inter-module-communication-via-events.md) Decision 5). **그래서 "매칭 0건인가?"를 아는 유일한 방법은 추천 쿼리를 실제로 돌리는 것**이다 — 서버가 `NO_MATCH`를 확정 시점에 미리 알려주려면 클라이언트가 요청하지도 않은 추천 조회를 선행해야 하고, 이는 요구5(매물 요청 시점은 클라가 결정)와 정면으로 충돌한다. ① 지역 게이트만은 요구1이 명시적으로 요구한 예외다.
- 추천 응답 사실(코드 확인): v1 `RecommendationResponse`는 0건일 때 `suggestions`(`reason=NO_MATCH` + 조정 액션)를 채운다 — 즉 **"no-match"라는 개념은 이미 추천 응답 쪽에 있다**. v2가 흐름 응답에 `NO_MATCH` 코드를 두면 같은 사실을 두 곳에서 표현하는 셈이다. 다만 v2는 제안을 쓰지 않기로 했으므로(요구3) v1 응답을 그대로 쓰면 안 쓰는 `suggestions`가 실려 온다.
- 카탈로그 사실(코드 확인): `diagnosisQuestions`의 문항은 `field`가 서로 겹치지 않아(`region`·`purpose`·`university`·`district`·`conditions`·`monthlyRent`·`arcStatus`) **`field`만으로 유일하게 식별된다** — 예외질문을 한 건 더 얹어도 스키마 변경이 없다. 반면 저장된 `step`은 코드의 선언 순서와 **같은 순서를 중복**해 표현하고, 한 step에 문항이 둘일 수 있어(③ university/district) 조회 키로도 부족하다. 다만 캐노니컬 시드 `DiagnosisCatalogSeedChangeUnit`(order 0000)은 **환경당 정확히 1회**라 이미 배포된 환경에는 새 문항이 적재되지 않는다 → 데이터 진화 changeUnit이 따로 필요하다([migration-policy §8](../database/migration-policy.md)·[ADR-0032](./0032-mongodb-migration-runner.md)).
- 제약: v1의 추천 0건 응답(`suggestions`)과 그 시드(`diagnosisSuggestions`의 `NO_MATCH`)는 v1 코드가 사용 중이다 — 이를 전역 삭제하면 v1이 깨진다(요구4와 충돌). "종료코드/`NO_MATCH` 코드"는 에러가 아니라 정상 흐름 결과이므로 공통 에러 코드가 아니라 응답 `data` 안 결과값으로 표현해야 한다.

## Decision

**진단 질의응답의 서버 주도 흐름을 `/api/v2/diagnoses`의 `POST /start`(클라 주도 시작) + `POST /next`(대화)로 신설하고, 진행 상태를 v1과 분리된 flow-session에 담으며, 매 응답을 정상 `200` `data` 안의 결과코드(태그드 유니온)로 표현한다. 서버가 주도하는 것은 질문·분기까지이고 시작과 매물 조회 시점은 클라이언트가 정한다. v1은 계약을 바꾸지 않는다.** 세부는 다음과 같다.

1. **`/api/v2`에 새 컨트롤러만 추가한다.** `DiagnosisV2Controller(@RequestMapping("/api/v2/diagnoses"))`에 **`POST /start`**(본문 없음 — 진단을 처음부터 시작하고 ① 지역 질문 반환)와 **`POST /next`**(본문은 기존 `AnswerRequest` — 현재 문항 답 1개, **필수**: 답(`field`)이 없으면 `INVALID_INPUT`)를 둔다. v1 컨트롤러·서비스 계약·`SecurityConfig`·`package-info` 의존 화이트리스트는 변경하지 않는다.
2. **진행의 단일 정본은 `pendingField`(서버가 직전에 낸 문항의 field)다.** 정본 순서는 `DiagnosisFlowStep` enum의 **선언 순서**로 고정한다 — `REGION → PURPOSE → UNIVERSITY_OR_DISTRICT(저장된 purpose로 university|district) → CONDITIONS → MONTHLY_RENT → ARC_STATUS`. 세션은 문항을 낼 때 그 `field`를 기록하고, 다음 `/next`는 (a) `request.field == pendingField`로 **순서를 강제**하고 (b) `ofField(답한 field).next()`로 **다음 문항을 정하며** (c) 다음이 없으면(마지막 `ARC_STATUS`) **자동 확정**한다. 답 필드의 null 여부로 진행을 추론하지 않는 이유는 `validateComplete`가 `conditions`(④)를 필수로 보지 않고 ⑥ `arcStatus` 파생이 `conditions`를 교차 기록해 추론이 불안정하기 때문이다(`validateComplete`는 자동 확정 시 정합 백스톱).
   - **진행 슬롯 수를 따로 세지 않는다(`cursor` 없음).** 흐름에는 정본 6슬롯에 **없는** 문항이 끼어들 수 있어 "몇 개 답했나"와 "무엇을 물었나"가 어긋나기 때문이다 — ① 지역 예외질문(`regionRetry`)이 뜬 시점의 진행 수는 1이고 그 순서상 다음은 `purpose`라, 기대 답을 진행 수로 역산하면 `regionRetry` 답이 "현재 단계의 답이 아님"으로 **거부되고** `purpose` 답은 **통과해** 버린다(예외질문을 무시하고 0건 지역으로 진행). 낸 문항을 그대로 기억하면 예외질문도 일반 문항과 **같은 규칙**으로 검증되고, 흐름 제어 문항을 더 붙여도 세션에 상태를 추가할 필요가 없다.
   - 그래서 별도 상태 enum(`FlowState { IN_FLOW, AWAITING_REGION_RETRY }`)도 두지 않는다 — 그건 "지금은 진행 수를 믿지 마"라고 표시하던 우회로였고, `pendingField`가 그 역할을 흡수한다. 진행 수와 `pendingField`는 **같은 사실을 두 벌로** 들고 있어 어긋날 여지만 남기므로 후자만 남긴다. 부수 효과로 ① 지역 게이트 조건이 인덱스 우연(`cursor == 1`)이 아니라 의도(`"region".equals(답한 field)`) 그대로가 된다.
   - `UNIVERSITY_OR_DISTRICT`는 `university`·`district` **둘 다** 이 슬롯으로 되돌린다(`ofField`) — 어느 쪽을 답했든 다음은 `CONDITIONS`다.
3. **v2 진행 상태는 별도 aggregate·컬렉션에 둔다.** `DiagnosisFlowSession { userId, draft(Diagnosis 누적 초안), pendingField }`를 도메인 포트 `DiagnosisFlowSessionRepository`(구현은 infrastructure)로 **`diagnosisFlowSessions` 컬렉션**에 저장한다. v1의 `diagnoses`/IN_PROGRESS 초안을 공유하지 않는다 — (a) "사용자당 IN_PROGRESS 1건" 제약과 충돌 회피, (b) `pendingField` 같은 절차 필드로 v1 `Diagnosis` 애그리거트를 오염시키지 않기 위해서다. **완료 시에만** `draft.complete()`로 정본 `Diagnosis`를 만들어 **기존 `diagnoses` 컬렉션에 저장**(v1 이력·상세·추천 읽기 경로 재사용)하고 세션은 삭제한다.
4. **매 응답은 정상 `200`의 결과코드(태그드 유니온)로 표현한다.** `DiagnosisFlowResponse { FlowResultCode resultCode, QuestionResponse question?, Long diagnosisId? }`, `FlowResultCode = NEXT_QUESTION | RESTART | COMPLETED | TERMINATED`(UPPER_SNAKE, null payload 필드는 직렬화 생략). 이는 에러가 아니므로 공통 에러 래퍼(`error`)나 `DiagnosisStatus`(IN_PROGRESS/COMPLETED, 도메인 전이 enum)에 넣지 않는다. **`RESTART`·`TERMINATED`는 "클라이언트가 다음에 할 행위"(재시도·진단종료)를 알리는 제어 코드**이고, 나머지 둘은 흐름 위치를 알린다. **`NO_MATCH`는 이 enum에 없다** — 아래 결정 9 참조.
5. **① 지역만 서버가 미리 필터링하고, 그 예외질문은 카탈로그의 일반 question으로 낸다.** 방금 ① 지역을 답했으면(답한 field가 `region`), `region`만 채운 경량 `RecommendationCriteria`(`size=1`)로 `recommendByCriteria`를 동기 호출해 **매칭 존재만** 확인한다([ADR-0002](./0002-inter-module-communication-via-events.md) D5) — 서버가 미리 필터링하는 **유일한 지점**이다(요구5). 0건이면 **`NEXT_QUESTION`**으로 "다른 지역 방을 찾아보시겠어요?" 문항을 내고 `pendingField=regionRetry`로 기록한다(정본 슬롯을 전진시키지 않는다). 이 문항은 서버 합성 문구가 아니라 **`diagnosisQuestions` 카탈로그의 일반 문항**(`field: "regionRetry"`, `select: {type:"SINGLE", max:1}`, `options: [{code:"YES"}, {code:"NO"}]`)이라 문구·번역 정본이 다른 6단계와 같은 곳에 있다(요구6 — ADR-0028·ADR-0029 그대로 적용). 카탈로그는 순서를 담지 않으므로 이 문항도 다른 문항과 **동등하게** 들어가고, 정본 6슬롯 밖(흐름 제어)이라는 사실은 코드에만 있다. 별도 결과코드(`REGION_RETRY`)를 두지 않는다 — 질문은 질문일 뿐이다. 다만 `regionRetry`의 답(`YES`/`NO`)은 **흐름 제어 응답**이라 `Diagnosis`의 어떤 필드로도 저장되지 않는다(진단 답 필드가 아니라 `applyAnswer`를 타지 않는다). 단 그 응답이 결정 12의 폐기 기록을 트리거해 **그때까지의 draft는 `DISCARDED` 진단으로 저장**된다 — 저장되지 않는 건 `YES`/`NO` 값이지 진단 초안이 아니다.
6. **카탈로그는 문항의 표현만 담고 순서를 담지 않는다 — 조회 키는 `step`이 아니라 `field`다.** `diagnosisQuestions` 문서에서 `step`을 걷어내고(`{ field, question, select, options, active }`) `field` UNIQUE 인덱스로 유일성을 강제한다(부트스트랩 initializer — 인덱스는 Mongock 소관이 아니다). 경계는 이렇다: **문구·선택지·번역 = 카탈로그(배포 없이 수정), 순서·분기·답 처리 = 코드**(`DiagnosisFlowStep` + `DiagnosisAnswerApplier`).
    - `step`을 카탈로그에 두면 **같은 순서를 코드와 DB 두 곳이** 표현하는데(선언 순서 = `step`), 정작 DB의 `step`으로는 아무것도 결정할 수 없다 — 순서는 결정 2가 코드로 강제하고, 한 step에 문항이 둘일 때(③ university/district) 어느 것을 낼지는 저장된 `purpose`가 정하기 때문이다(ADR-0028: 카탈로그에 분기 메타를 두지 않는다). 남은 역할이 "조회 키"뿐인데 그마저 `field`가 더 정확하다(step은 1:N, field는 1:1) — 그래서 `findByStep` + "목록에서 field로 택일"이 `findByField` 한 번으로 줄고 `selectQuestion` 헬퍼가 사라진다.
    - **`step` 번호 자체는 코드에 남는다** — v1 `GET /questions/{step}`의 경로 파라미터를 `field`로 옮기는 데(`ofStep(step).field()`), 그리고 응답의 `question.step` 표시값으로 쓰인다. 즉 `step`은 **순서가 아니라 v1 호환 번호**다.
    - 카탈로그를 순서의 정본으로 삼는 반대 방향은 택하지 않았다 — 답 처리(`DiagnosisAnswerApplier`)가 `field`로 스위치하고 `Diagnosis`가 타입 박힌 필드를 갖는 한 **문항을 데이터만으로 늘릴 수 없고**, ②→③ 분기 의존·⑥→④ 파생 교차기록 때문에 자유로운 재정렬도 안전하지 않다. 얻는 것 없이 잘못된 시드가 컴파일 타임 보장을 런타임 장애로 바꾼다.
7. **그 문항의 적재는 시드(0000) + 기배포 환경용 changeUnit(0005)이다.** 캐노니컬 시드 `DiagnosisCatalogSeedChangeUnit`(order 0000)에 `regionRetry` 문항을 넣고, 0000을 이미 실행한 환경을 위해 `DiagnosisRegionRetryQuestionChangeUnit`(order 0005)을 신설한다 — (step 1, field `regionRetry`) 문항을 제거 후 삽입하는 **멱등** 적재라 신규 환경(0000이 이미 적재)과 결과가 같다. 인덱스는 부트스트랩, 시드·데이터 진화는 Mongock이라는 분업을 지킨다([migration-policy §8](../database/migration-policy.md)·[ADR-0032](./0032-mongodb-migration-runner.md)). 문항을 코드가 아니라 데이터로 두기로 한 결정(위 5)의 필연적 대가이자 이점 — 문구 교정에 배포가 필요 없다.
8. **예외질문의 예/아니오는 클라이언트가 행할 행위 코드로 옮긴다.** `pendingField=regionRetry`인 세션에 `code=YES`가 오면 세션을 삭제하고 **`RESTART`**(재시도)를, `code=NO`면 세션을 삭제하고 **`TERMINATED`**(진단종료)를 반환한다 — **둘 다 코드만** 내려간다(YES/NO 외 code는 `INVALID_INPUT`). `YES`에서 서버가 곧장 ① 지역 질문을 밀어 넣지 않는 이유는 요구7이다: 재시도는 클라이언트가 `POST /start`로 건다. 그래서 진행 중 세션을 되돌리는 전이(`resetToRegion`)는 두지 않는다 — 세션은 시작에서 생기고 터미널에서 삭제될 뿐이다.
9. **빌더 완성 시 서버가 자동 확정하되, 매칭을 조회하지 않는다 — `NO_MATCH` 결과코드를 두지 않는다.** 마지막 슬롯(⑥ `arcStatus`)을 답했으면 `draft.complete(now)`로 확정(`IN_PROGRESS → COMPLETED`)·저장하고 **`COMPLETED` + `diagnosisId`만** 반환한 뒤 세션을 삭제한다(재검증 실패는 `INVALID_INPUT`). 확정 **시점**은 서버가 판단하지만(요구2), **매물을 언제 조회할지는 클라이언트가 정한다**(요구5). no-match를 결과코드로 미리 주려면 서버가 여기서 추천 쿼리를 돌려야 하는데 **그건 클라이언트가 요청한 적 없는 조회**라 요구5와 배치된다 — 0건인지는 클라가 추천을 요청한 그 응답의 그 조회 응답의 결과코드(`NO_MATCH`)가 알려주면 충분하고, 그게 사실을 아는 유일한 경로다(위 Context "매칭 경로 사실"). **`NO_MATCH`를 없앤 게 아니라 아는 시점으로 옮긴 것**이다 — 결정 10의 추천 응답에 그대로 있다. 서버가 미리 필터링하는 지점은 결정 5의 ① 지역 게이트 **하나뿐**이다.
10. **v2 전용 추천 엔드포인트를 신설한다.** `GET /api/v2/diagnoses/{id}/recommendations` — v1 §7과 필터·매핑·페이지 계약이 같고 **차이는 조정 제안 문구·액션이 없다는 것 하나**다(`V2RecommendationResponse { resultCode, content, markers, page }`). v1은 0건일 때 `suggestions { reason:"NO_MATCH", message, actions[] }`로 **사유와 제안을 한 덩어리로** 주는데, v2는 제안을 쓰지 않기로 했으므로(요구3) 그 덩어리에서 **사유만 떼어** 최상위 `resultCode`(`MATCHED`/`NO_MATCH`, 항상 존재)로 둔다 — **제안을 안 쓰는 것과 사유를 안 주는 것은 다르다.** v1 응답을 그대로 쓰면 안 쓰기로 한 제안이 실려 오고, v1에 `?suggestions=false` 같은 옵션을 다는 건 v1 계약 변경이라 요구4와 충돌한다. 검증·소유권·조건 매핑·listing 호출은 v1과 **공유 컴포넌트(`DiagnosisRecommendationReader`)로 단일화**해 소유권 규칙이 두 벌이 되지 않게 한다(결정 14와 같은 취지). `NO_MATCH`는 에러가 아니라 정상 결과다.
11. **v2는 조정 제안(`suggestions`)을 쓰지 않는다 — v1 자산은 그대로 둔다.** v1의 `suggestions` 6개 클래스·`RecommendationResponse.Suggestions`·`diagnosisSuggestions` 시드는 v1 추천 0건 경로가 사용 중이므로 **전역 삭제하지 않는다**(삭제하면 v1이 `500`·응답 계약 파괴 → 요구3의 문자 그대로 이행과 v1 무변경(요구4)이 상호배타). v2는 그 기계를 **참조하지 않을** 뿐이며, 그 실현은 결정 10의 전용 엔드포인트다 — 응답에 `suggestions` 필드 자체가 없으므로 0건이어도 제안이 없다(요구3의 취지 충족). ① 지역 예외질문은 이 `suggestions` 기계와 **무관**하다 — 그건 제안이 아니라 카탈로그 문항이다(요구6, 위 결정 5).
12. **① 지역 0건으로 끝난 시도만 `diagnoses`에 `DISCARDED`로 남긴다.** 지역 예외질문에 답이 오면 부분 답을 `Diagnosis.discard(now)`(`IN_PROGRESS → DISCARDED`, **완결성 검증 없음** — 부분 답이 정상)로 저장한 뒤 세션을 지운다. 목적은 **수요 분석** 하나다: "어느 지역을 원했는데 매물이 없었나". **"예"(재시도)도 남긴다** — 안 남기면 사용자가 다른 지역으로 완주했을 때 원래 원했던 지역이 증발한다. 이 경로는 ① 지역을 답한 뒤에만 도달하므로 `draft.region`이 있는 게 보장된다.
    - **그 외 이탈(답하다 앱을 닫음)은 남기지 않는다.** 이탈은 요청으로 오지 않아 **돌아왔을 때(`/start`)에야** 알 수 있는데, 그러면 (a) 영영 안 돌아온 사용자는 집계에서 통째로 빠지고 (b) 시각이 실제 이탈 시각이 아니라 재시작 시각(며칠 뒤일 수 있음)이 된다. 부정확한 데이터를 쌓느니 안 남긴다 — `/start`는 이전 세션을 그냥 덮어쓴다. 지역 0건 경로는 그 자리에서 응답이 와 시각이 정확하고 신호도 명확해 예외다.
    - **v1 충돌이 없는 이유**: 목록 조회가 상태로 스코프돼 있다 — 이력·최근은 `COMPLETED`만, v1 초안 조회(`findInProgressByUserId`)는 `IN_PROGRESS`만 본다. 그래서 `DISCARDED` 행은 어느 쪽에도 잡히지 않는다.
    - **다만 id로 직접 오는 경로는 자동으로 막히지 않는다** — 상세(`GET /diagnoses/{id}`)와 추천(v1 §7·v2-3)은 `findById` + 소유권만 보므로 **명시적으로 `DISCARDED`를 404로 거절**한다(`DiagnosisService.getDetail`·`DiagnosisRecommendationReader.read`). 소유권으로는 못 막는다: 폐기 기록은 **본인 것**이고 진단 id가 **순차 발급**이라 추측 가능하다. 미완주 부분 답으로 추천을 돌리는 것도 무의미하다. 이 가드가 없으면 내부 분석 기록이 API로 새어 나간다(`discardedIsNotFetchableByRecommendations`·`discardedIsNotFetchableByDetail`이 가드).
    - 그래서 `RESTART`·`TERMINATED` 응답에 **폐기 진단의 `diagnosisId`를 싣지 않는다**(결정 8) — `COMPLETED`의 `diagnosisId`는 "이걸로 매물을 조회하라"는 뜻인데 폐기 기록 id는 클라가 쓸 데가 없고(다음 행동은 `POST /start`), 같은 필드에 다른 뜻을 담으면 오히려 계약이 흐려진다. 무엇보다 **내부 기록으로 가는 열쇠를 클라에 쥐여줄 이유가 없다**. 결정 3이 세션을 분리한 이유(미완성 초안이 v1 초안 조회에 잡힘)가 여기선 발생하지 않는다.
    - **대가(수용함)**: `Diagnosis`에 `reason`이 없어 **"포기(아니오) vs 재시도(예)"가 데이터에서 구분되지 않는다**(둘 다 `region=BUSAN`·`purpose=null`로 똑같이 보인다). 1차 신호("부산 수요 N건, 매물 0건" = `DISCARDED` + `purpose=null`)는 온전하다. 그 이상이 필요해지면 절차 필드를 애그리거트에 넣는 대신(결정 3이 거부) 전용 기록 컬렉션을 검토한다.
    - `submittedAt`은 **종료 시각**으로 통일한다(`COMPLETED`=확정 시각, `DISCARDED`=폐기 시각) — 상태가 어느 종료인지 이미 말해주므로 타임스탬프를 둘로 나누지 않는다.
13. **시작은 클라이언트가 주도하고, 서버는 흐름을 임의로 되살리지 않는다.** `POST /start`는 진행 중 세션이 있어도 **무조건 버리고** 새 세션(빈 `draft`, `pendingField=region`)을 만들어 ① 지역 질문을 반환한다 — 교체는 삭제 후 삽입이 아니라 **`userId` 기준 원자적 upsert**(`upsertByUserId` 포트 → `findAndModify(upsert, returnNew)`)로 한다. 삭제와 삽입 사이에 낀 동시 요청(시작 버튼 더블탭·클라 재시도)이 "사용자당 1 세션" UNIQUE와 경합해 `DuplicateKeyException`(→ 500)이 되기 때문이다. 유니크 인덱스와 **같은 조건으로 upsert**하는 것은 이미 `recentListings`가 쓰는 방식이다 — 진단을 하다 홈으로 나갔다 다시 시작하면 서버가 남은 진행 정보를 보지 않고 **언제나 처음부터**다(요구7). 대칭으로 **진행 중 세션 없이 온 `POST /next`는 `400 DIAGNOSIS_SESSION_NOT_FOUND`**("진행 중인 진단이 없습니다. 진단을 다시 시작해 주세요.")로 막는다(신규 `ErrorCode` + `DiagnosisFlowSessionNotFoundException`) — 재개나 암묵적 시작을 허용하면 시작 주도권이 서버로 되돌아가기 때문이다. 클라이언트는 이 에러나 `RESTART`를 받으면 `/start`로 다시 건다. 중복 확정 방지는 "터미널에서 세션 삭제 + 세션 없으면 400"이 대신한다.
14. **공유 로직은 헬퍼로 추출해 v1·v2가 공용한다.** `applyAnswer`(답 적용·파생 조건 주입)·`toCriteria`(조건 매핑)·문항 번역/③ 분기 계산·추천 조회(`DiagnosisRecommendationReader` — 페이지/정렬 검증·소유권·조건 매핑·listing 호출)를 공유 컴포넌트로 추출하고 v1 `DiagnosisService`는 이를 위임한다(동작 보존 리팩터, v1 통합·RestDocs 테스트가 회귀 가드). 분기·파생 규칙을 v2에 복제해 정합 버그 표면을 늘리지 않기 위해서다. **문항 조회는 v1·v2 모두 `field` 지목**이다(결정 6) — 카탈로그가 `field`로 문항을 식별하므로 `findByField(field)`가 1건을 돌려주고, v1은 클라가 준 `step`을 `DiagnosisFlowStep.ofStep(step).field()`로 옮겨 조회한다(step 3만 저장된 purpose로 분기). 파급은 내부 구현에 그치고 **v1 계약은 불변**이다 — 카탈로그에 `regionRetry`가 추가돼도 v1 `GET /questions/1`은 `region`을 그대로 낸다(`DiagnosisMongoIntegrationTest.step1PicksRegionNotRegionRetry`·`DiagnosisFlowStepTest.v1StepNumbersArePinned`가 가드).

|---|---|---|---|
| v1 엔드포인트를 서버 주도로 개조 | 엔드포인트 1벌 | 하위 호환 파괴, 요구4(v1 무변경) 위반, 클라 회귀 | 요구4가 명시적으로 버전 상향을 요구 |

## Consequences

- 긍정: 클라이언트가 `step`·확정 시점·분기를 몰라도 되어 앱-서버 결합이 낮아진다. 동시에 **시작·매물 조회 시점은 클라가 쥐어** 화면 전환(홈 이탈 후 재시작)·페이지네이션·정렬을 앱이 자연스럽게 제어한다. 지역 조기 차단으로 "0건인데 끝까지 진행" 비효율이 사라진다. 확정 응답이 `diagnosisId`만이라 가볍고, 매물 조회 경로가 v1 추천 하나로 단일화된다. 예외질문이 카탈로그에 있어 문구·번역 수정이 **배포 없이** 가능하고 정본이 한 곳이다. v1 계약은 그대로라 회귀 위험이 낮다. 진행 상태가 별도 컬렉션이라 v1 도메인이 오염되지 않는다. 결과코드가 정상 흐름이라 에러 채널이 깨끗하다.
- **공급 없는 지역의 수요**가 데이터로 남는다(`DISCARDED` + `region` + `purpose=null`) — 새 컬렉션·포트 없이 상태값 하나와 전이 하나로 얻었고, v1은 그 값을 아예 못 본다. 기록 지점을 "그 자리에서 정확히 알 수 있는" 지역 0건 하나로 좁혀 `/start`는 예전처럼 단순한 upsert로 남았다.
- 주도권 경계가 코드에 한 줄로 드러난다: 서버가 `recommendByCriteria`를 부르는 곳은 `regionHasMatch`(① 게이트) **하나**이고, 그 외의 모든 매물 조회는 클라이언트의 요청(`GET /recommendations`)에서 출발한다. 확정 응답이 매칭과 무관해져 6단계 완료 경로에서 listing 호출이 사라졌다(확정마다 1회 절약).
- 부정/트레이드오프: **`diagnoses`에 사용자 데이터와 분석 기록이 섞인다** — `DISCARDED` 행은 어떤 조회에도 안 잡히지만 컬렉션은 커지고, 이 컬렉션을 직접 읽는 쿼리는 이제 상태를 반드시 걸러야 한다. **포기와 재시도가 구분되지 않는다**(결정 12의 수용한 대가). **답하다 이탈한 시도는 아예 안 남으므로 "어느 문항에서 이탈하나"는 알 수 없다** — 그건 의도된 범위 밖이다. v2 추천 엔드포인트가 v1 §7과 **거의 같은 응답을 내는 두 번째 경로**가 된다(차이는 `suggestions` 유무뿐) — 공유 `DiagnosisRecommendationReader`로 조회·소유권·검증은 단일화했지만 매핑·컨트롤러·스펙 절은 두 벌이다. 0건일 때 클라가 결과 화면에 진입해서야 알게 되어 왕복이 1회 더 든다(그 대신 서버가 매 확정마다 추천을 미리 돌리지 않는다). 진단 모듈에 v2 전용 타입(컨트롤러·`DiagnosisFlowService`·`DiagnosisFlowSession`/포트/구현·결과 DTO·순서/상태 enum)이 늘어 표면적이 커진다. 확정 직후 **추천을 받으려면 왕복이 1회 더** 든다(인라인 동봉 대비 — 대신 클라가 시점·페이지·정렬을 정한다). **진행 중 이탈 후 재시작은 항상 초기화**라 중간 복구가 없다 — 답을 6개까지 채우고 홈으로 나갔다 돌아와도 처음부터 다시 답해야 하고, `RESTART`(지역 예외질문 "예")도 앞서 답한 지역을 되살리지 않는다(요구7의 대가 — 문항 수가 적고 "이어서 하기" 요구가 없어 수용). **카탈로그 조회가 `step` 목록에서 `field` 단건으로 바뀌었다**(결정 6) — v1도 `ofStep(step).field()`로 옮겨 조회하도록 내부가 바뀌었고(계약은 불변), `field` 유일성이 이제 **UNIQUE 인덱스로 강제**된다(시드가 중복을 넣으면 적재 시점에 실패한다 — 예전엔 목록 순서에 따라 조용히 갈렸다). 공유 헬퍼 추출로 v1 `DiagnosisService` 파일이 바뀐다(동작 보존이지만 "문자 그대로 v1 무변경"은 아님 — 테스트로 가드). v2 완료 진단이 v1과 같은 `diagnoses` 컬렉션에 섞여 이력/추천 조회에 함께 나타난다(의도된 재사용) — `NO_MATCH`여도 진단은 확정·저장되므로 이력에 남는다. v2가 쓰지 않는 v1 `suggestions` 자산이 남는다(데드코드 아님 — v1 추천 0건 경로가 사용).
- 후속 작업: `diagnosisFlowSessions` `userId` 유니크 인덱스는 기동 시 부트스트랩 initializer(`DiagnosisFlowSessionIndexInitializer`)가 멱등 생성한다(인덱스=부트스트랩, 시드·데이터 진화만 Mongock — [migration-policy §8](../database/migration-policy.md)·[ADR-0032](./0032-mongodb-migration-runner.md)). 지역 존재확인 오버헤드가 크면 `listing::api`에 `count`/`exists` 포트 신설. 버려진 세션(시작만 하고 이탈)은 `/start`가 덮어쓰므로 누적되지 않지만, 재방문 없는 사용자 몫이 쌓이면 TTL 검토. v2 완료 진단 출처 구분이 필요해지면 태깅 검토. 스펙·US·시퀀스 문서 동반 갱신.

## Validation

- v2 흐름은 `DiagnosisFlowServiceIntegrationTest`(Testcontainers)가 검증한다 — 시작/순서 강제/자동 확정/지역 0건 → `NEXT_QUESTION`(`field=regionRetry`)/예=`RESTART`/아니오=`TERMINATED`/`COMPLETED`가 `diagnosisId`만 싣고 추천은 없음. **시작 주도권**은 "진행 중 세션이 있어도 `/start`가 기존 진단 정보를 버리고 처음부터 시작", "세션 없는 `/next`는 `400 DIAGNOSIS_SESSION_NOT_FOUND`", "터미널 직후 재-POST도 세션이 없어 거부(중복 확정 방지)"로 못 박는다.
- **매물 조회 주도권**은 `autoConfirmDoesNotQueryRecommendations`가 `verify(listing, times(1))`로 고정한다 — 6단계 전 구간에서 listing 호출은 ① 지역 게이트 **1회뿐**이며, 확정 시 매칭을 미리 확인하면 2회가 되어 실패한다. 이 결정이 조용히 되돌아가는 걸 막는 가드다. 이어서 `fullFlowWithNoFinalMatchStillCompletes`가 "최종 0건이어도 `COMPLETED`이고, no-match는 클라가 추천을 조회한 응답의 `resultCode=NO_MATCH`로 드러난다"를, `getRecommendationsReturnsListings`·`getRecommendationsOfOtherUserRejected`가 v2 추천 엔드포인트의 매핑·소유권을 검증한다.
- **지역 수요 보존**은 `regionRetryNoLeavesDiscardedDiagnosis`(포기)·`regionRetryYesAlsoLeavesDiscardedDiagnosis`(재시도도 남김)가, **기록 범위**는 `startDoesNotRecordAbandonedSession`(답하다 이탈한 세션은 `/start`가 덮어쓸 때 남기지 않음)이 못 박는다. **v1 무오염**은 `discardedIsInvisibleToV1InProgressLookup`이 `findFirstByUserIdAndStatus(IN_PROGRESS)`가 비어 있음을 확인한다. 각 경로가 진단을 정확히 1건만 남기는지도 함께 본다.
- v1 통합 테스트가 공유 헬퍼 추출의 동작 보존을 가드한다. 이 변경의 유일한 v1 회귀 표면인 **"`step 1`에 문항이 2건이어도 `GET /questions/1`은 `region`을 낸다"** 는 `DiagnosisMongoIntegrationTest.step1PicksRegionNotRegionRetry`가 두 문항을 함께 시드해 직접 가드한다(문항 선택이 목록 순서가 아니라 `field` 지목인지 확인).
- **v2 응답 계약**은 `DiagnosisV2DocsTest`가 문서로 못 박는다 — `/api/v2/diagnoses/*` 스니펫 22종(성공 10: 시작·`NEXT_QUESTION` 4종(일반 문항·지역 예외질문·④ 다중 선택·⑤ 월세 범위)·`COMPLETED`·`RESTART`·`TERMINATED`·추천 `MATCHED`/`NO_MATCH` / 에러 12)을 생성해 v1과 함께 OpenAPI3 명세(Swagger UI)에 합류시킨다. v1 스니펫은 `DiagnosisDocsTest`가 그대로 담당한다(두 버전이 공존하므로 문서도 분리).
  - `AnswerRequest`의 **세 형태를 모두** 예시로 남긴다 — `code`(단일 선택)·`codes`(④ 다중 선택)·`min`/`max`(⑤ 월세 범위). 형태별 예시가 없으면 필드 서술이 "이런 값도 올 수 있다"고 말할 뿐 실제 모양은 클라가 런타임에 받아봐야 안다. 같은 이유로 ⑤ 월세 **문항**(`select.type=NUMBER_RANGE`·`options` 빈 배열 — "질문은 곧 선택지 목록"이라는 가정에서 의도적으로 분리된 예외, 결정 6·US-2-5)의 응답 예시도 남긴다. v1(`POST /answers`)에도 없던 `min`/`max` 예시를 함께 채웠다.
  - 흐름 응답이 태그드 유니온이라 payload를 **nullable optional 하나로 묶지 않고 `resultCode`별로 스니펫을 나눈다** — `COMPLETED` 스니펫에 `question`이 optional로 남아 있으면 "확정에도 질문이 올 수 있다"는 거짓을 문서가 말하게 된다. 각 스니펫은 실제로 실린 필드만 문서화하고(`NON_NULL` 생략과 일치), 실리지 **않는다**는 사실은 `question`/`diagnosisId`의 `doesNotExist()` 단정이 가드한다.
  - 주도권 경계도 문서에 남는다 — `COMPLETED` 스니펫이 `diagnosisId`만 싣고(매물 없음), `NO_MATCH` 스니펫에 `suggestions`가 없다는 것이 v1 스니펫과 나란히 드러난다. 다만 "확정 시 추천을 미리 조회하지 않는다"는 **호출 횟수** 불변식은 문서로 드러나지 않으므로 `autoConfirmDoesNotQueryRecommendations`가 계속 정본 가드다.
- 지역 조기 게이트의 매칭 정의(`recommendByCriteria`의 PUBLISHED + `address.city` + ACTIVE roomOffer)가 최종 추천과 동일 필터의 상위집합인지 확인한다 — 상위집합이어야 "지역엔 있는데 최종 조건으로 0건"만 남고 그 반대(게이트에서 막혔는데 실은 매물이 있음)가 없다. `COMPLETED`인데 추천이 빈 경우는 이제 **어긋남이 아니라 정상**이다(서버가 매칭을 약속하지 않는다).
- 재검토 시점: v1 은퇴(그때 suggestion 전역 삭제·v2 승격 재검토), 또는 지역 존재확인 호출량이 성능 이슈가 될 때.
